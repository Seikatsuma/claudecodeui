# Repository guidance

## Backend code

For every task that creates, modifies, refactors, or reviews backend code under `server/`, load and follow `$backend-module-standards` from `.agents/skills/backend-module-standards/SKILL.md`. Apply it only to backend code; do not impose those architecture rules on the frontend.

## Вид ленты ответов (`src/components/chat/view/subcomponents/Markdown.tsx`)

Три грабли, каждая стоила отдельной выкатки «ничего не изменилось»:

1. **Уровни заголовков сдвинуты.** `#` рендерится в `<h2>`, `##` — в `<h3>` и так
   далее: в документе остаётся один `h1`. Правила вида `.prose h1` в `index.css`
   промахиваются мимо и выглядят как рабочие.
2. **Размер заголовка задаётся в компоненте, не в CSS.** Utility-классы Tailwind
   (`text-[22px]`) лежат в слое выше `components`, поэтому `index.css` их не
   перебьёт. Меняешь кегль — меняй класс в `Markdown.tsx`.
3. **Абзац — это `div`, а не `p`,** и подзаголовок отличается от жирного слова
   только классом `md-subheading`, который ставит сам разметчик. Чистым CSS их не
   различить: `:only-child` считает теги и не видит текст вокруг, поэтому целился
   и в `текст <strong>слово</strong> текст`, разрывая абзац.

Правка вида проверяется снимком отрисованного элемента с ЖИВЫМ CSS с сервера, а
не `grep`'ом по `dist` — обе прошлые ошибки прошли проверку файлами.

4. **Копия выделением — с пустой строкой между абзацами** (25.09.26,
   `utils/copyParagraphBreaks.ts`). Отступ абзаца в буфер не попадает, и в
   Telegram пункты слипались. На время `copy` между выделенными блоками
   верхнего уровня (`[data-md-copy-root]`) ставится `<div><br></div>`, до кадра
   убирается. Буфер не подменяем — пропал бы жирный. После вставки выделение
   ставится заново: Chrome иначе обрывает копию на старом конце выделения.

## Копирование ответа выделением (`chat/utils/copyParagraphBreaks.ts`, 25.09.26)

Пустые строки между абзацами и номера «1.», «2.» нумерованного списка браузер
в копию не кладёт: отступы и маркеры рисует CSS. Обработчик `copy` на мгновение
вставляет их в DOM настоящим текстом и убирает до кадра. Буфер через
`clipboardData` не подменять — пропадёт жирный. У списка на это время
`list-style: none`, иначе Word и Заметки покажут «1. 1.». Номер берётся с экрана:
`ol.start` + `li.value`. Выделение от первой буквы пункта стоит правее вставленного номера — его начало растягивается на номер, иначе первый «1.» терялся. Компонент `ol` в `Markdown.tsx` `start` не передаёт,
поэтому список после текста и на экране, и в копии начинается с 1.

## Изоляция веб-пользователей: смотреть на КАЖДЫЙ рождающийся процесс (12.09.26)

Разделение аккаунтов делалось дважды и оба раза оказывалось неполным, потому
что проверялось только чтение данных — чьи чаты видно в списке. Но у сервера
есть второй, куда более опасный канал: процессы, которые он запускает от имени
пользователя.

Встроенный терминал (`shell-websocket.service.ts`) отдавал оболочке
`...process.env` целиком и вообще не получал опознанного пользователя —
websocket-шлюз передавал запрос чату, но не терминалу. Значит `CLAUDE_CONFIG_DIR`
был серверный, то есть общий каталог владельца площадки. Приглашённый набрал
`/login` — и OAuth-вход владельца был перезаписан чужим. Владелец при этом
увидел не ошибку, а тихую смену аккаунта; приглашённый — «CLI не
аутентифицирован», потому что интерфейс спрашивал про ЕГО каталог, где пусто.

**Правило.** Любое место, где рождается дочерний процесс (`pty.spawn`,
`child_process.*`, SDK с параметром `env`), обязано получать каталог настроек
и ключ из `shared/web-user-runtime.ts`, а не из окружения сервера. Если
пользователя определить не удалось, а `OPEN_REGISTRATION` включён — процесс не
запускается вовсе: молча писать в чужой каталог хуже, чем отказать.

**Второе правило, из той же истории.** Расчёт «чей это пользователь и куда ему
можно писать» существует ровно в одном экземпляре. Копия этого расчёта в чате
жила отдельно и не знала про терминал — та же болезнь, что у двух разошедшихся
сверок ленты сообщений в тот же день: копия отстаёт молча, и найти это можно
только по жалобе человека.

**Третий раз, 25.09.26 — «вошёл ли человек в Claude».** Терминал писал вход в
папку человека, экран «вход есть» его видел, а чат пускал не-владельца только
с ключом API из настроек (правило 02.09, до починки терминала) — вошедший
подпиской получал «Add your Anthropic API key». Теперь одна проверка:
`shared/claude-login.ts` (settings.json + `.credentials.json`; истёкший
короткий ключ при живом ключе продления = вошёл, CLI продлит сам; сервер
ключ не продлевает). Чат спрашивает `hasOwnClaudeAccess` (ключ сайта ИЛИ вход
в своей папке), отказ — `CLAUDE_LOGIN_REQUIRED` с путём «Настройки → Агенты».
Гостю процессы (чат, терминал) не получают ключи Claude из окружения сервера
(`isolateInheritedClaudeAuth`): CLI предпочёл бы их входу гостя. Тесты
сервера гонять с `env -u CLAUDE_CONFIG_DIR -u OPEN_REGISTRATION -u DATABASE_PATH`:
чат, запущенный с сайта, наследует эти переменные, и тесты входа и терминала
читают живые папки. Проба целиком — временный экземпляр (`env -i HOME=/tmp/…
DATABASE_PATH=/tmp/… OPEN_REGISTRATION=true SERVER_PORT=…`), гость по
приглашению, поддельный `.credentials.json` в его папке, `chat.send` в сокет:
«OAuth session expired» = чат пустил и CLI взял вход гостя.

## Группы чатов и архив в шапке (13.09.26)

- На месте переключателя пресетов в шапке — `ChatGroupSelector`: «В архив» первым пунктом, ниже группы свежие сверху, галочка у текущей. Порядок задан Егором, не переставлять. Пресет включается во вкладке настроек «Пресеты».
- Хранилище: `chat_groups` (по `account_dir`, как и чаты) + колонка `sessions.group_source`. Имя группы копируется в `group_label` — по нему список слева рисует заголовки без второго запроса; переименование группы обязано обновить копии.
- `group_source='manual'` (в т.ч. «без группы» = manual + NULL) автоматика не пересматривает никогда. `auto` пересматривается при каждой сборке события `session_upserted` (смена названия). Группы старой кнопки «Organize by topic» (`group_id` без источника) не трогаются.
- При общих словах выигрывает старшая по созданию группа — новая не перетягивает чаты.
- 16.09.26 — раскладка моделью (`chat-groups/chat-group-classifier.ts`), цель Егора «80–90% моих чатов в группах» (по словам было 44%). Фоном раз в 5 мин Sonnet без инструментов/настроек, входом аккаунта чатов (`CLAUDE_CONFIG_DIR=account_dir`); выключить — `CHAT_GROUP_CLASSIFIER=off`. Решение модели = `group_source='ai'`; подбор по словам его не сбрасывает, если слова не совпали. Новая тема — `group_hint`, группа создаётся с `CANDIDATE_MIN_CHATS`=3 чатов. `group_hint_title` = название, которое модель видела: совпадает — чат повторно не разбирается (иначе расход подписки на каждом проходе).
- В группы не попадают чаты программ: `origin='auto'`, папки `/tmp`, сегмент `e2e*` (`isMachineMadeChat`), а тестовые названия модель отдаёт в skip. Тестовые прогоны 13.09 шли через настоящий терминал (`origin=terminal`), поэтому одного `origin` мало.
- Кнопка-часы «Последние чаты» — в строке «Проекты / папка / архив / командная строка» (`SidebarHeader`), не отдельной строкой под «Новым сеансом» (Егор 16.09). Нажата — все чаты по дням без групп; выбор общий через `hooks/useSessionListView.ts` (`localStorage` `sidebar-session-list-view`).
- Время чата в списке = `sessions.updated_at`. На общем экземпляре (OPEN_REGISTRATION) наблюдатель файлов выключен, и `updated_at` отставал на часы (18.09); его сверяет `providers/services/session-activity-sync.service.ts` — раз в 15 с `stat` файлов известных чатов, у изменившихся — время последней записи user/assistant (не mtime: служебные строки без времени); с базой сверяет каждый проход — другие писатели (синхронизатор при загрузке списка, веб) ставят туда mtime/время запуска. Без рассылки `session_upserted` (ставит «внимание», уходит всем пользователям); список перечитывается раз в минуту (`AppContent`).
- Архив из шапки убирает чат из списка слева (`removeSessionFromList`), но не уводит со страницы; `session_upserted` для архивных не рассылается, поэтому убирать приходится на клиенте.
- `ActionMenu` c `portal`: слушатель прокрутки окна висит с перехватом — прокрутку внутри самого меню он обязан пропускать, иначе длинный список закрывается при попытке листать.

## Два блока в строке «Проекты» — второй сервер (20.09.26)

Строка под поиском разделена надвое: «Проекты» — дела этого сервера, второй
блок — дела, которые ведутся отсюда, а живут на другой машине (Егор обвёл эту

- Хранилище: `projects.server_scope` (`'main'`/`'second'`, NOT NULL) и
  `sessions.server_scope` (NULL = как у папки). Чат переносится между блоками
  признаком в базе, а НЕ переездом файла переписки: файл остаётся в своей
  папке, чат продолжается как обычно, перенос отменяется тем же пунктом меню.
- Выбранный блок и его название живут в `hooks/useServerScope.ts` (как вид
  списка в `useSessionListView`), а не ходят пропсами: их спрашивают шапка,

- Отбор делает `Sidebar.tsx` один раз (`scopedProjects`), дальше контроллер,
  список, выбор папки и «Пульс» получают уже отобранное. Папка попадает в
  блок, если приписана к нему сама ИЛИ в ней есть перенесённый туда чат.
- Во втором блоке ведущей (плоский вид) становится папка с
  `serverScope === 'second'`, а не отмеченная звёздочкой: звезда стоит на
  главной папке этого сервера, и «Новый сеанс» заводил бы чат не в том месте.
- Лента `GET /sessions/recent` принимает `serverScope`: отбирать после выдачи
  нельзя, страница берётся по 40 чатов.

## Черновик в поле ввода принадлежит чату (13.09.26)

Ключ `draft_input_<scope>`, где scope — id чата, а у нового чата до первой
отправки — `project:<projectId>` (`draftScopeFor` в `chat/utils/chatStorage.ts`).
Раньше ключ был по проекту и подменялся только при смене проекта, поэтому
текст ехал за человеком из чата в чат одного проекта.

В `useChatComposerState` эффект СОХРАНЕНИЯ черновика обязан стоять выше эффекта
ПОДМЕНЫ и сверяться с `draftOwnerRef`: в кадре переключения область уже новая, а
`input` ещё старый — без сверки текст чата А пишется в чат Б. Отправка стирает
черновик той области, откуда отправили (`submitDraftScope`), а видимое поле —
только если человек всё ещё в том чате: пока грузятся вложения, он мог уйти.
Старые черновики по проекту один раз переезжают в открытый чат
(`adoptLegacyProjectDraft`).

## Агенты — в своих комнатах, не в группе сайта (22.09.26)

- Агент запускается через `agent-rooms.js`: `systemd-run --user --scope --slice=ccui-agents.slice -p MemoryHigh=2G -- claude …` (обёртка в `spawnSurvivableClaude`). `--scope` делает exec — PID, каналы, «Стоп», live-runs те же. Образец — jupyterhub/systemdspawner.
- Зачем: 22.09 агенты + их ffmpeg/сборки заняли 2,73 ГБ группы службы при MemoryHigh 2,5 ГБ, ядро душило всю группу вместе с сервером (memory.pressure full ~90%), новый сервер после перезапуска 15+ мин не открывал порт → «Секунду, обновляюсь».
- Срез `~/.config/systemd/user/ccui-agents.slice` (копия `deploy/ccui-agents.slice`): MemoryHigh 4G, MemoryMax 5G, MemorySwapMax 1G, CPUWeight 40. Пользовательскому менеджеру делегированы только cpu/memory/pids — IOWeight там не работает.
- Проба на старте и раз в 10 мин (раз в минуту после неудачи) создаёт пустую комнату; не прошла — агенты запускаются напрямую, как раньше, и уходит оповещение в TG (не чаще раза в час). Каждый агент через 3 с сверяется по /proc/<pid>/cgroup — не в своей комнате → тоже оповещение. Выключить: `CLOUDCLI_AGENT_ROOMS=off`. Проверка: `cat /proc/<pid агента>/cgroup` → `…/ccui-agents.slice/ccui-agent-….scope`.

## Чаты переживают перезапуск сайта (13.09.26)

- Агент — дочерний процесс сервера. У службы `KillMode=process` (drop-in `99-keep-agents.conf`), но этого мало: при штатной остановке SDK на `process.exit` шлёт SIGTERM всем своим детям. Проба: штатная остановка родителя — агент погиб; SIGKILL родителя — агент доделал задачу.
- Поэтому агент запускается через `spawnClaudeCodeProcess` → `survivor-runs.js`: во время остановки `kill` — пустая операция; запись `~/.cloudcli-shared/live-runs/<pid>.json` (чат, номер разговора, каталог аккаунта).
- После старта `adoptSurvivors` усыновляет живые записи (PID жив И в cmdline есть `claude` и `stream-json`): реестр считает чат работающим (второй запуск в тот же чат отклоняется), изменения файла переписки рассылаются `session_upserted` с `detachedRun: true` (страница перечитывает переписку даже у «работающего» чата), по завершении — `chat_subscribed isProcessing:false` всем вкладкам. «Стоп» — SIGTERM процессу.
- `useChatSessionState` не перечитывает переписку, пока чат `isProcessing`. Поэтому по завершении пережившего агента порядок строго: сначала `complete` (НЕ `chat_subscribed isProcessing:false` — его вкладка отбрасывает через `ifStartedBefore`, если после подписки отметила чат работающим), потом (через 1,5 с) `session_upserted`. Промежуточные шаги такого агента во вкладке живьём не видны — появляются разом, когда он закончит.
- Этап пережившего агента (15.09.26): без него плашка до конца работы писала «Ожидает модель» — Егор остановил чат с идущим 4 мин проверяющим (105 шагов в subagents/*.jsonl, в переписке чата тишина). `readTranscriptPhase` читает хвост переписки (512 КБ): незакрытый Agent/Task → `agents` (число), другой незакрытый инструмент → `tool` (имя), последним результат → `reading`, размышление/текст/сообщение человека → `thinking`/`writing`/`requesting` ; незакрытые вызовы закрывают только текст/размышление модели и `[Request interrupted…]` (прерывание бывает без `tool_result`), но НЕ сообщение человека и не `<task-notification>` — они приходят посреди идущей команды. Пересчёт — при смене mtime в `pollSurvivors`; смена → `onPhase` → `run_phase` с `detail` всем вкладкам; `chat_subscribed` несёт `phase`/`phaseDetail` (только для пережившего), клиент ставит их в плашку.
- `jsonl_path` у чата, начатого с сайта, заполняет периодический обход файлов — минуты спустя. История (`claude-sessions.provider.ts`) при пустом пути ищет файл по номеру разговора в папке аккаунта запроса и сразу запоминает путь (`setJsonlPathIfMissing`); без этого открытая вкладка перечитывала пустую историю и не показывала ответ.
- Первая выкатка этой правки идёт поверх старого кода: штатный перезапуск убьёт работающие чаты. Без потерь — только SIGKILL главного процесса (служба сама поднимется: `Restart=on-failure`).


## Метка работы на живых событиях (13.09.26)

`seq` у каждой работы (`chatRunRegistry.startRun`) свой и начинается с 1, а
вкладка отбрасывает события с `seq <= lastSeqRef[sid]` — защита от повторной
доставки. Счётчик был по ЧАТУ и не сбрасывался между работами: после долгой
работы вкладка помнила большой номер и молча выбрасывала ВСЕ события следующей,
включая сигналы «думает / работает». Сервер при этом считал чат занятым.

Теперь каждое событие несёт `runStartedAt` (время запуска работы), его же
возвращает `chat_subscribed`. Клиент (`chat/utils/liveRunCursor.ts`) при новой
метке обнуляет счётчик чата; подписка передаёт известную метку, и сервер при
несовпадении досылает работу с начала. Старая вкладка без метки: если её номер
больше, чем вообще есть у работы, — досылка тоже с начала.

Лента без воды. Размышления в ленте по умолчанию скрыты (`showThinking: false`
в `hooks/useUiPreferences.ts`) — и у тех, кто уже сохранил «показывать»:
одноразовая метка `uiPreferences.thinkingHiddenByDefault.v1`. Текст в размышлениях
ЕСТЬ — первое допущение «они пустые» оказалось неверным и проверялось по записи

## Скорость: где на самом деле уходило время (замер 14.09.26)

- **Как мерить.** Каждый запрос отдельно (`curl` с `auth-token` из localStorage) даёт 3–100 мс; в браузере на этой же машине те же запросы шли 1–2,5 с. ## Лента держит место сама: `useScrollAnchor` (15.09.26)
- Жалоба: «листаю вверх — возвращает в одну и ту же точку и не даёт загрузить остальное». Замер `~/tmp-ccui/perf/scroll_snapback_probe.py <метка> <чат>` (номер первого на экране сообщения С КОНЦА должен только расти): до правки 3 отката за 150 шагов, отрезки по 10+ шагов у верха без подгрузки.
- Опора — первая `.chat-row` на экране (не самая верхняя: её ключ меняется, когда в «Ход работы» вливаются ранние действия); запоминается `offsetTop`. ResizeObserver на `.chat-rows` (и каждое событие прокрутки) при смене высоты возвращает сдвиг опоры в `scrollTop`. Ловит всё: порции, дорисовку `content-visibility`, раскрытие блоков. Поэтому у `.chat-messages-pane` стоит `overflow-anchor: none` — иначе Chrome вернул бы сдвиг второй раз. Строкам нужен общий `offsetParent` (панель `relative`); не делать `.chat-rows`/`.chat-row` позиционированными.
- Палец на стекле / инерция ПОСЛЕ КАСАНИЯ (колесо и полоса прокрутки — пишем сразу, иначе у «ложного верха» стоит до 8 шагов; TanStack PR #1280) / отскок (`scrollTop < 0`) — `scrollTop` не пишем (на iPhone обрывает бросок), сдвиг держит `margin-top: -N` у `.chat-rows`; через 140 мс без прокрутки (или `scrollend`) отступ снимается и прокрутка прибавляется в одном кадре. Приём TanStack Virtual PR #1189 / issue #1287. `scrollToBottom` и возврат на вкладку сначала сбрасывают отложенный сдвиг. Касание без движения дольше 1 с и уход приложения в фон (`visibilitychange`/`pagehide`) движением не считаются — iOS может не прислать `touchend`, и отступ висел бы.
- Порцию берём за три экрана до верха (`topPreloadMargin`); после отрисовки порции и после переноса сдвига сторож проверяется вручную (IntersectionObserver не видит нового пересечения, если сторож не выходил из зоны).

простояла 11 минут с красным индикатором, не сделав ни одной попытки

вынесено отдельно потому, что `WebSocketContext` живёт в React и без DOM не

делом, до всякой очереди, и разбор очереди — вместо прежних собственных веток
